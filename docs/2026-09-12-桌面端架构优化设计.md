# PT-depiler 桌面端架构优化设计

## 1. 文档信息

| 项目     | 内容                                                            |
| -------- | --------------------------------------------------------------- |
| 状态     | 提案                                                            |
| 基线     | 2026-09-12 当前工作区，浏览器扩展代码清理后的 Tauri 桌面架构    |
| 目标读者 | 项目维护者、功能开发者、测试与发布负责人                        |
| 适用范围 | Vue 应用、TypeScript 业务包、Tauri IPC、Rust 平台服务和本地数据 |
| 不包含   | 产品功能重设计、站点适配规则重写、移动端适配                    |

本文给出 PT-depiler 从“浏览器扩展迁移后的可运行形态”演进到“边界清晰、数据可靠、默认安全的桌面应用”的目标架构。方案采用渐进迁移，不要求一次性重写现有站点、下载器、媒体服务器或备份服务。

## 2. 背景与结论

项目已经完成关键的平台迁移：Vue 单页应用通过 Tauri 调用 Rust，Rust 统一处理 HTTP、Cookie、文件下载和调度；原浏览器扩展的 content script、service worker、Chrome API 与构建依赖已大幅清理。

当前主要矛盾不再是“能否脱离浏览器扩展运行”，而是“旧扩展架构是否适合长期承载桌面应用”。现状仍保留 `background`、`offscreen`、本地消息路由和 WebExtension 风格持久化，导致以下风险：

1. Cookie 已加密，但下载器密码、API Token、S3 Secret 和备份密钥仍可能明文写入 `storage.json`。
2. 消息协议允许声明与实现脱节，当前已有 `setDownloadHistoryStatus` 无 handler 的实际案例。
3. Pinia、Tauri Store、IndexedDB、Cookie 文件和内存任务之间没有统一事务与迁移边界。
4. `CSP=null`、宽泛的 `ptd_fetch` 与主窗口平台权限共同扩大了 WebView 被利用后的影响范围。
5. `packages` 反向依赖 `entries`，应用层、领域层和基础设施层职责交叉。
6. 后台任务依赖前端窗口和内存状态，应用退出后重下载任务会丢失。

优化目标不是增加更多抽象，而是建立四个明确边界：**应用用例边界、领域扩展边界、平台能力边界、持久化边界**。

## 3. 现状架构

```text
Vue Views / Pinia
        |
        v
src/entries/messages.ts
本地消息名 -> handler 映射
        |
        v
background / offscreen 业务模块
        |
        +-----> site / downloader / mediaServer / backupServer / social
        |
        v
全局 Axios Tauri Adapter
        |
        v
Tauri invoke
        |
        v
Rust http.rs / state.rs / storage.rs / scheduler.rs
        |
        +-----> PT 站点、下载器、媒体服务器、备份服务
        +-----> storage.json、Cookie 加密文件、本地文件
```

### 3.1 当前模块职责

| 模块                         | 当前职责                               | 主要问题                                             |
| ---------------------------- | -------------------------------------- | ---------------------------------------------------- |
| `src/entries/options`        | UI、Pinia、启动、业务服务装配          | 启动依赖导入副作用，初始化结果不可观测               |
| `src/entries/messages.ts`    | 单进程业务调用路由                     | 字符串索引削弱类型约束，handler 完整性只在运行时检查 |
| `src/entries/background`     | 存储、Cookie、调度等平台逻辑           | 名称与职责仍来自扩展时代，业务和平台逻辑混合         |
| `src/entries/offscreen`      | 搜索、下载、备份、用户信息等核心用例   | 既编排业务又直接访问多种存储                         |
| `src/packages/*`             | 站点和外部服务适配实现                 | 部分 package 反向导入 `entries` 层类型和服务         |
| `src/extends/axios`          | Axios 到 Tauri HTTP 的兼容层           | 修改全局 Axios 状态，影响范围隐式                    |
| `src-tauri/src/http.rs`      | IPC、HTTP、curl、登录窗口、Cookie 转换 | 单文件职责过多，平台路径耦合                         |
| `src-tauri/src/storage.rs`   | 通用 JSON KV 持久化                    | 无敏感字段隔离、schema version 和事务                |
| `src-tauri/src/scheduler.rs` | 周期事件和延迟重试                     | 任务不持久化，依赖前端窗口存活                       |

### 3.2 当前数据所有权

| 数据                 | 当前载体                     | 所有者问题                     |
| -------------------- | ---------------------------- | ------------------------------ |
| 配置与 metadata      | Pinia + `storage.json`       | UI 内存和后台直接写入可能失步  |
| 下载历史             | IndexedDB                    | 恢复时与其他数据无法原子提交   |
| 搜索快照、辅种任务   | Store / IndexedDB            | 存储策略分散，缺少统一版本迁移 |
| Cookie               | Rust 内存 + AES-GCM 加密文件 | 安全性较好，可保留为独立安全域 |
| 下载器和远程服务凭据 | metadata / config            | 与普通 UI 配置同级明文保存     |
| 延迟重下载参数       | TypeScript `Map`             | 应用退出或窗口重建后丢失       |

## 4. 架构目标与原则

### 4.1 质量目标

| 维度     | 当前估计 | 目标 | 可验证结果                                     |
| -------- | -------: | ---: | ---------------------------------------------- |
| 可维护性 |     5/10 | 8/10 | package 不反向依赖 UI；模块职责可单独测试      |
| 安全性   |     5/10 | 8/10 | 磁盘不可检索凭据明文；主窗口最小权限；启用 CSP |
| 可靠性   |     5/10 | 8/10 | 任务重启恢复；备份恢复失败可回滚；写盘错误可见 |
| 可测试性 |     6/10 | 8/10 | 用例可脱离 Vue/Tauri 测试；IPC 有契约测试      |
| 扩展性   |     7/10 | 8/10 | 现有动态实体工厂保留，扩展仅依赖稳定端口       |

### 4.2 设计原则

1. **单向依赖**：UI 依赖应用层，应用层依赖领域接口，基础设施实现接口；领域包不依赖 `entries`。
2. **单一数据所有者**：持久化数据由 Rust Repository 管理，Pinia 只保存视图状态和服务端数据的可丢弃缓存。
3. **敏感值与普通配置分离**：配置只保存 `secretRef`，实际凭据由系统 Keyring 管理。
4. **显式启动**：服务注册、数据迁移和监听器安装均由 `bootstrapApp()` 控制并返回结果。
5. **能力最小化**：前端只能调用完成产品用例所需的窄接口，不能自然获得任意平台能力。
6. **错误必须可见**：禁止关键持久化、调度和状态更新路径使用空 `catch`。
7. **渐进替换**：先建立新边界，再逐个迁移调用方；每个阶段保持可构建、可测试和可回滚。

## 6. 关键设计

### 6.1 显式启动与服务注册

当前 `main.ts` 通过导入 `service/index.ts` 触发 handler 注册、调度监听和数据修复。目标启动流程如下：

```text
create infrastructure adapters
        |
run storage migrations
        |
register application services
        |
assert command/query coverage
        |
restore persisted tasks
        |
mount Vue application
```

`bootstrapApp()` 返回 `AppContext`，失败时展示可诊断的启动错误页，不挂载处于半初始化状态的业务 UI。

```typescript
interface AppContext {
  commands: CommandBus;
  queries: QueryBus;
  events: AppEventBus;
  dispose(): Promise<void>;
}

async function bootstrapApp(): Promise<AppContext>;
```

启动阶段必须验证所有公开 command/query 都存在实现。事件监听器必须返回取消订阅函数，并在应用退出或窗口重建时释放。

### 6.2 用例接口替代字符串消息路由

现有 `messages.ts` 的目的，是隔离 UI 与原扩展多上下文通信。桌面单进程下不再需要模拟浏览器消息协议，但仍需要稳定的应用接口。

建议将其拆为：

- Command：执行有副作用的操作，例如推送下载、保存配置、恢复备份。
- Query：读取数据，例如下载历史、站点用户信息、备份列表。
- Event：通知已完成的状态变化，例如 `DownloadStatusChanged`。

协议类型使用封闭映射，不继承 `Record<string, ...>`，注册表在初始化完成后冻结。过渡期可以保留 `sendMessage()` 外观，但内部转发到新的 command/query bus，并为旧消息建立完整性测试。

```typescript
interface CommandMap {
  UpdateDownloadStatus: {
    input: { downloadId: number; status: DownloadStatus };
    output: void;
  };
}

type CommandName = keyof CommandMap;
```

不在消息层序列化函数、类实例或 DOM。动态站点配置只在领域适配边界解析。

### 6.3 应用层与领域包边界

`site`、`downloader`、`mediaServer`、`backupServer` 和 `social` 保留动态工厂模式，但只依赖稳定端口：

```typescript
interface IntegrationContext {
  http: HttpClient;
  settings: SettingsReader;
  secrets: SecretReader;
  clock: Clock;
  logger: Logger;
}
```

应用层创建实体时注入 `IntegrationContext`。领域包不得导入：

- `@/messages.ts`
- `@/storage.ts`
- `@/options/*`
- Tauri API

跨层共享类型移动到 `domain` 或对应 package；例如 Cookie 备份 DTO 不应由 `entries/shared` 提供给 `backupServer`。

### 6.4 持久化与一致性

目标是由 Rust 管理持久化数据，采用 SQLite 保存结构化数据，系统 Keyring 保存密钥，Cookie 继续使用独立认证加密文件。前端不能执行原始 SQL，只能调用受约束的 Repository 命令。

建议数据域：

| 数据域                       | 目标存储          | 原因                                                |
| ---------------------------- | ----------------- | --------------------------------------------------- |
| 普通设置、站点 metadata      | SQLite            | 支持 schema、迁移和事务                             |
| 用户历史、下载历史、搜索快照 | SQLite            | 统一查询和备份事务边界                              |
| 持久化任务                   | SQLite            | 支持状态机、恢复和幂等                              |
| 凭据                         | OS Keyring        | 避免配置文件出现明文                                |
| Cookie                       | 现有 AES-GCM 文件 | RFC Cookie Store 结构适合整体序列化，现有实现已验证 |
| 临时 UI 状态                 | Pinia 内存        | 可重建，不需要持久化                                |

数据库必须包含 `schema_migrations`。每个迁移具备版本号、前置版本、执行事务和失败诊断。应用只允许从相邻受支持版本迁移；未知的更高版本必须拒绝启动写操作。

Pinia Store 分为两类：

1. `view stores`：筛选条件、弹窗状态、加载状态，可直接修改。
2. `resource stores`：Repository 查询结果的缓存，只能通过 action 刷新，不自行持久化。

所有保存接口返回明确结果，不能吞掉错误：

```typescript
type SaveResult =
  { ok: true; revision: number } | { ok: false; code: "CONFLICT" | "IO_ERROR" | "VALIDATION_ERROR"; message: string };
```

`revision` 用于发现旧快照覆盖新数据。高频统计写入允许批处理，但关闭应用前必须 flush。

### 6.5 SecretStore 与敏感数据迁移

普通配置只保存引用：

```json
{
  "id": "downloader-1",
  "type": "qBittorrent",
  "address": "http://127.0.0.1:8080",
  "usernameSecretRef": "downloader/downloader-1/username",
  "passwordSecretRef": "downloader/downloader-1/password"
}
```

SecretStore 必须满足：

- key 由 `{category}/{entityId}/{field}` 构成，不把敏感值写入日志。
- 读取只返回给发起具体用例的 Rust 或受控适配器，不提供“列出全部明文”命令。
- 删除业务实体时同步删除凭据；失败进入待清理队列。
- 前端表单读取现有凭据时只获得 `configured: true`，不会自动回填真实值。
- 修改凭据采用“空值表示保持不变、显式操作表示删除”的协议。

历史数据迁移流程：

```text
读取旧 storage.json
  -> 识别敏感字段
  -> 写入 Keyring
  -> 回读验证
  -> 用 secretRef 替换明文
  -> 原子保存普通配置
  -> 清除旧值并记录迁移版本
```

迁移中任一步失败时保留旧数据并停止删除，避免凭据丢失。完成后扫描应用数据目录，确认不存在已迁移的明文值。

### 6.6 HTTP 能力与安全策略

用户可以配置任意 PT 域名、局域网下载器和私有备份服务，因此不能使用固定域名白名单。应采用“来源类型 + 已登记 endpoint + 用户授权”的动态策略。

```text
业务用例创建 HttpRequest
        |
        v
HttpPolicy 根据 resourceId 解析已登记 endpoint
        |
        +-- site: 仅允许站点配置域及显式登录跳转
        +-- downloader: 允许登记的主机和端口，包括局域网
        +-- backup/media: 允许对应实体 endpoint
        +-- public API: 允许内置定义声明的 endpoint
        |
        v
过滤协议、方法、请求头、重定向和目标地址
        |
        v
reqwest / 限定条件下的 curl fallback
```

最低安全规则：

- 只允许 `http` 和 `https`，拒绝 `file`、`data`、`ftp` 等协议。
- 请求必须携带资源身份，不能依赖仅用于日志的 `siteId`。
- `Authorization`、`Cookie`、`Host` 等敏感头由受控适配器生成，普通 UI 不得任意注入。
- 重定向每一跳重新执行策略，并阻止向不同 origin 转发认证头。
- 下载器可以访问回环和私网地址；站点与公共 API 默认不能通过 DNS 重绑定进入私网。
- 设置响应体上限；大文件走流式下载命令，不通过 base64 IPC 常驻内存。
- 保留 Axios 兼容层作为过渡，不再修改 `axios.defaults.adapter`；为不同资源创建独立 `HttpClient`。

Tauri 安全配置应启用 CSP，并按窗口分 capability：

| 窗口         | 能力                                                      |
| ------------ | --------------------------------------------------------- |
| `main`       | 受控业务命令、必要 dialog/file 能力                       |
| `site-login` | 不授予业务 invoke 能力，只允许 HTTP(S) 导航与 Cookie 同步 |
| 测试窗口     | 仅 debug 构建启用，使用隔离数据目录和密钥                 |

未使用的 notification、global-shortcut 插件和 capability 应删除；未来确有功能使用时再按用例恢复。

### 6.7 持久化任务调度

任务由 Rust 调度服务持有，前端只提交任务，不保存定时器真相。

```text
queued -> scheduled -> running -> succeeded
                      |       |
                      |       +-> retry_wait -> scheduled
                      +----------> failed / cancelled
```

建议任务字段：

| 字段                       | 含义                                             |
| -------------------------- | ------------------------------------------------ |
| `id`                       | 稳定任务 ID                                      |
| `kind`                     | `redownload`、`auto_backup`、`refresh_user_info` |
| `payload`                  | 版本化 JSON，只保存恢复任务所需的数据引用        |
| `run_at`                   | 下一次执行时间                                   |
| `status`                   | 状态机当前状态                                   |
| `attempt` / `max_attempts` | 重试控制                                         |
| `lease_until`              | 防止崩溃后永久停在 running                       |
| `last_error`               | 脱敏错误摘要                                     |

任务处理器必须幂等。启动时将过期 lease 的 `running` 任务恢复为 `scheduled`；任务成功后与业务状态更新在同一事务内提交。前端窗口关闭时，后台仍能继续执行不依赖 UI 的任务。

### 6.8 备份与恢复

新备份格式定义为 v2，旧格式保持只读兼容：

- 使用带版本头的 manifest。
- 使用 PBKDF2 或 Argon2id 派生密钥，参数写入 manifest。
- 使用 AES-256-GCM 等 AEAD 认证加密，每个文件使用独立 nonce。
- 默认不导出 SecretStore；导出凭据必须由用户显式选择并设置备份口令。
- 恢复前先完成 ZIP 路径、大小、manifest、密文认证和 schema 校验。

恢复采用三阶段：

```text
Validate
  校验格式、版本、字段、大小和解密结果
        |
Stage
  导入临时数据库，构建恢复预览和冲突报告
        |
Commit
  关闭写入 -> 创建恢复点 -> 原子替换 -> 重载缓存
        |
失败时恢复原数据库与 Cookie 文件
```

跨 SQLite、Keyring 和 Cookie 文件无法获得真正的单事务，应使用恢复 journal 记录每一步，并提供补偿操作。应用崩溃后根据 journal 继续提交或回滚。

### 6.9 Rust 模块拆分

拆分以职责和测试边界为依据：

- `http/policy.rs`：URL、目标地址、请求头和重定向授权。
- `http/reqwest_transport.rs`：默认传输实现。
- `http/curl_transport.rs`：仅 macOS 条件编译的兼容路径。
- `auth/cookie_vault.rs`：Cookie 转换、加密持久化和查询。
- `auth/login_window.rs`：登录窗口生命周期和同源约束。
- `ipc/*_commands.rs`：Tauri DTO 与应用服务的薄适配。
- `persistence/repositories`：数据库事务和查询。

IPC command 不应直接包含复杂业务规则。核心服务接收普通 Rust 参数，以便不启动 Tauri Runtime 就能测试。

### 6.10 错误、日志与可观测性

建立跨 TypeScript/Rust 的稳定错误码：

| 分类           | 示例                               |
| -------------- | ---------------------------------- |
| `VALIDATION_*` | 配置、URL 或备份格式错误           |
| `AUTH_*`       | 登录失效、Secret 不存在            |
| `NETWORK_*`    | 超时、DNS、TLS、被站点拒绝         |
| `STORAGE_*`    | 数据库冲突、迁移失败、磁盘写入失败 |
| `TASK_*`       | 调度失败、重试耗尽、任务取消       |
| `INTERNAL_*`   | 未分类缺陷                         |

日志使用结构化字段：`operationId`、`resourceId`、`taskId`、`errorCode`、耗时和重试次数。禁止记录 Cookie 值、密码、Token、完整 Authorization、含敏感 query 的 URL 和未过滤响应正文。

用户可恢复的错误进入 UI 通知；不可恢复的启动错误进入诊断页；后台失败写入任务状态和本地诊断日志。任何错误都不应仅依赖控制台输出。

## 7. 数据与接口契约

### 7.1 IPC 约束

- DTO 使用 `camelCase`，Rust 与 TypeScript 各维护一端类型并通过 fixture 契约测试验证。
- 所有写命令携带 `operationId`；可重试操作还携带幂等键。
- 时间统一使用 UTC Unix 毫秒，展示时再转换时区。
- 二进制大对象不通过 JSON/base64 往返，改用临时文件句柄或流式命令。
- IPC 返回 `{ ok, data, error }` 的稳定 envelope，业务错误不使用任意字符串解析。

### 7.2 数据兼容策略

| 变更类型     | 策略                                         |
| ------------ | -------------------------------------------- |
| 新增可选字段 | 兼容读取，迁移时补默认值                     |
| 字段改名     | 一个发布周期双读，统一单写新字段             |
| 敏感字段迁移 | Keyring 回读成功后才清除旧值                 |
| 删除字段     | 先停止读取，再在后续迁移删除                 |
| 备份格式升级 | 新版写 v2，同时保持 v1 只读导入              |
| IPC 变更     | 先新增新 command，迁移调用方后删除旧 command |

## 8. 测试与质量门禁

### 8.1 测试分层

| 层级            | 覆盖内容                                                |
| --------------- | ------------------------------------------------------- |
| 领域单元测试    | 站点字段解析、下载器请求生成、备份格式和状态机          |
| 应用用例测试    | 使用内存端口测试搜索、下载、恢复和错误补偿              |
| Repository 测试 | SQLite migration、事务、并发 revision 和崩溃恢复        |
| IPC 契约测试    | TypeScript DTO 与 Rust command 的字段、错误和二进制语义 |
| 平台集成测试    | Keyring、Cookie 文件、登录窗口、reqwest/curl 行为       |
| 桌面冒烟测试    | 登录、搜索、下载器推送、备份恢复和应用重启              |

296 个站点定义不适合逐站进行完整 E2E，但每个公共 schema 必须有 HTML/JSON fixture；包含自定义解析函数的站点定义必须至少有一个回归 fixture。站点定义变更时，只运行受影响 schema 和定义测试，主分支定期运行完整矩阵。

### 8.2 统一门禁

继续保留并扩展 `pnpm verify:desktop`：

```bash

pnpm build:dist

```

补充门禁：

- 依赖边界检查：阻止 `src/packages` 导入 `src/entries` 或 Tauri API。
- handler/command 覆盖检查：所有公开协议必须有实现和契约测试。
- 凭据扫描：测试数据目录中不得出现测试 secret 明文。
- 数据迁移测试：从每个仍支持的历史版本升级到最新版。
- 产物检查：禁止重新打包浏览器扩展入口和已删除依赖。
- macOS、Linux 构建和至少一个平台的安装后启动验证。

## 9. 分阶段实施计划

### Phase 0：冻结基线与修复已知缺陷

目标：在重构前消除会污染验证结果的实际缺陷。

任务：

- 为 `setDownloadHistoryStatus` 注册实现，并增加协议注册完整性测试。
- 修复持久化插件 `$dispose` 递归风险；保存失败向调用方返回错误。
- 清除关键路径空 `catch`，统一进入日志或任务失败状态。
- 删除确认无调用的 Rust notification、global-shortcut 插件和权限。
- 将 Vite 与 Vue Router 调整到受支持的版本组合。

验收：当前自动化全部通过；模拟写盘失败时 UI 能获得明确错误；下载重试失败最终进入 `failed`。

回滚：本阶段均为局部修复，可逐提交回滚，不改变数据格式。

### Phase 1：建立应用层和显式启动

目标：先形成新的依赖方向，不迁移数据载体。

任务：

- 新建 `app`、`application`、`domain/ports`、`infrastructure/tauri`。
- 实现 `bootstrapApp()` 和类型化 command/query/event。
- 用兼容适配器包装现有 `messages.ts` 与 `extStorage`。
- 选择搜索、下载历史两个用例作为首批迁移样板。

验收：迁移后的用例可用内存端口完成测试；启动失败不会挂载正常业务 UI；新代码不存在反向依赖。

回滚：保留旧 handler 入口，通过 feature flag 切换新旧用例实现。

### Phase 2：SecretStore 与 HTTP 安全边界

目标：优先消除明文凭据和过宽平台能力。

任务：

- 实现 Rust Keyring SecretStore 和历史敏感字段迁移。
- 引入 HTTP resource identity 与动态 endpoint policy。
- 启用 CSP，拆分 `main` 与 `site-login` capability。
- 将全局 Axios Adapter 改为显式客户端，先迁移下载器和备份服务。

验收：应用数据目录无法检索已配置测试凭据；未登记 endpoint、非法协议和跨源认证头被拒绝；真实局域网下载器仍可连接。

回滚：迁移版本只在 Keyring 写入、回读和配置替换全部成功后提交；旧字段保留一个兼容读取版本。

### Phase 3：统一 Repository 与数据迁移

目标：将多种业务持久化收敛到 Rust SQLite。

任务：

- 建立数据库 schema、migration registry 和 Repository command。
- 按 config、metadata、download history、snapshot、task 顺序迁移。
- Pinia 改为 view/resource cache，不再自动落盘整个 store。
- 引入 revision、事务和一致性错误。

验收：从真实旧数据副本迁移成功；重复执行迁移幂等；中途断电模拟不会产生半版本数据库；前端刷新后状态一致。

回滚：迁移前复制原 Store/IndexedDB；一个发布周期保留只读回退工具，不在成功迁移后立即删除旧文件。

### Phase 4：可靠调度与备份 v2

目标：使后台任务和恢复操作在退出、崩溃和失败场景下可恢复。

任务：

- 实现持久化任务状态机、lease、重试和幂等处理器。
- 将重下载、自动备份和用户信息刷新迁移到任务服务。
- 实现备份 v2、暂存恢复、journal 和回滚。
- 保持旧 CryptoJS 备份只读兼容，停止生成旧格式。

验收：任务执行前强制退出应用，重启后任务继续且不重复产生副作用；恢复任一步失败后原数据可用；篡改备份被 AEAD 校验拒绝。

回滚：调度器可按任务类型回退旧实现；v2 写入失败不影响 v1 导入能力。

### Phase 5：Rust 拆分、全量迁移与发布验证

目标：删除兼容层和扩展时代遗留边界。

任务：

- 按第 6.9 节拆分 `http.rs` 和 `state.rs`。
- 将剩余业务用例迁移到应用层，删除本地消息兼容路由。
- 将 `background/offscreen/webExtPersistence` 迁移到新目录并删除旧命名。
- 完成 macOS/Linux CI、安装包与真实服务冒烟矩阵。

验收：`src/packages` 无应用层反向依赖；旧消息总线和旧 Store 写路径无引用；全部质量门禁与真实冒烟通过。

回滚：仅在调用方迁移率达到 100%、连续两个发布周期无回退使用后删除兼容层。

```text
Phase 0 已知缺陷
   |
   v
Phase 1 应用边界 ----------------------+
   |                                  |
   +--> Phase 2 Secret/HTTP            |
   |                                  |
   +--> Phase 3 Repository ------------+
```

SecretStore 可以与 Repository 前期并行开发，但敏感字段正式迁移必须在配置 Repository 契约稳定后执行。备份 v2 依赖 SecretStore 和 Repository，因为它需要明确区分普通数据与凭据。

## 11. 风险与控制

| 风险                        | 影响                         | 控制措施                                                          |
| --------------------------- | ---------------------------- | ----------------------------------------------------------------- |
| 大量站点定义在迁移中回归    | 搜索或用户信息解析失败       | 保留 package 公共接口，先注入端口；使用 schema/definition fixture |
| Keyring 在 Linux 环境不可用 | 无法保存凭据                 | 启动时能力探测；禁止静默明文回退；给出明确修复指引                |
| SQLite 迁移损坏旧数据       | 用户配置或历史丢失           | 迁移前快照、事务、校验、版本化回滚工具                            |
| HTTP 策略过严               | 私有站点或局域网下载器不可用 | 按资源类型授权；提供可审计的用户授权流程和诊断结果                |
| HTTP 策略过宽               | SSRF 或凭据跨源泄漏          | 每跳校验、敏感头托管、DNS 解析后地址检查                          |
| 新旧路径并存时间过长        | 双写和行为分叉               | 每阶段定义迁移率和删除条件，禁止无期限兼容                        |
| 后台任务重复执行            | 重复下载或重复备份           | 幂等键、lease、事务提交和外部结果核验                             |
| 备份格式升级造成不可恢复    | 用户历史不可用               | v1 只读兼容、v2 round-trip fixture、发布前真实备份演练            |

## 12. 架构约束与自动检查

以下规则应转为自动化，而不是只存在于文档：

1. `packages` 和 `domain` 不允许导入 `entries`、Vue、Pinia 或 Tauri。
2. `application` 不允许直接调用 `invoke`、IndexedDB 或 Keyring。
3. 所有持久化写入必须经过 Repository 或 SecretStore。
4. 所有 HTTP 请求必须携带资源身份并经过 HttpPolicy。
5. 所有后台任务必须持久化并使用明确状态机。
6. 所有 IPC command 都有 DTO 契约测试和稳定错误码。
7. 所有敏感字段都必须在字段清单中标记，并通过落盘扫描测试。
8. 新增 side-effect import、全局 monkey patch 或空 `catch` 必须阻断检查。

可使用 ESLint `no-restricted-imports`、dependency-cruiser 或自定义 TypeScript AST 检查实现前端边界；Rust 使用模块可见性、Clippy 和集成测试保护边界。

## 13. 架构决策记录

| ID      | 决策                                    | 理由                                          | 代价                          |
| ------- | --------------------------------------- | --------------------------------------------- | ----------------------------- |
| ADR-001 | 采用渐进迁移，不重写站点生态            | 站点适配数量大，现有动态工厂有价值            | 需要短期维护兼容适配器        |
| ADR-002 | Rust 成为持久化数据唯一所有者           | 提供事务、迁移、任务恢复和统一备份边界        | 增加 IPC 与 Repository 代码   |
| ADR-003 | SQLite 保存结构化业务数据               | 替代 Store/IndexedDB 分散状态，支持事务和查询 | 需要一次性历史数据迁移        |
| ADR-004 | Keyring 保存非 Cookie 凭据              | 与 Cookie 安全等级对齐，避免磁盘明文          | 需要处理平台 Keyring 可用性   |
| ADR-005 | Cookie Vault 保持独立加密文件           | 当前实现已覆盖 RFC 语义和崩溃安全             | 恢复时需要 journal 协调多存储 |
| ADR-006 | HTTP 采用动态资源策略而非固定域名白名单 | 支持用户自定义站点和局域网服务                | 策略模型与诊断更复杂          |
| ADR-007 | Pinia 仅保存视图状态和资源缓存          | 避免双数据源和后台直写失步                    | 页面需要显式刷新和事件订阅    |
| ADR-008 | 备份 v2 使用版本化 AEAD 格式            | 同时提供保密性、完整性和未来升级能力          | 需保留旧格式只读兼容          |

## 14. 非目标

- 不在本次架构治理中统一重写 296 个站点定义。
- 不把所有外部服务请求移到 Rust；领域适配可继续使用 TypeScript，只需通过受控 HttpClient。
- 不追求在第一阶段删除所有旧命名和兼容代码。
- 不承诺后台执行需要用户交互的登录、验证码或文件选择流程。
- 不以微服务或多进程替代当前本地桌面应用形态。

## 15. 完成定义

满足以下条件后，架构优化可视为完成：

- 下载器、备份、媒体服务和站点 Token 不以明文存在应用数据文件中。
- 主窗口启用 CSP 并只拥有实际使用的最小 capability；登录窗口无业务 invoke 权限。
- 所有公开 command/query 均有实现、类型约束和契约测试。
- 配置、metadata、历史、快照和任务由 Rust Repository 统一管理并具有 schema migration。
- 延迟重下载、自动备份和用户信息刷新在应用重启后能够恢复。
- 备份恢复具备预校验、暂存、提交和失败回滚能力。
- `src/packages` 不再导入 `src/entries`，核心用例可使用内存端口单元测试。
- 全局 Axios Adapter、旧消息路由和 WebExtension 持久化兼容层已删除。
- macOS、Linux 自动门禁通过，真实站点、下载器和备份服务冒烟没有阻断项。
- 架构约束已由 CI 自动检查，而不是依赖代码评审人工记忆。
