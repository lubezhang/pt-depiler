# 下载服务管理 MVP 设计

## 目标

在桌面端提供独立的“下载服务管理”模块。模块以一个已配置下载器实例为工作上下文，从下载器设置列表进入；第一阶段以 Transmission RPC 为验收基准，用户可以：

- 查看当前下载服务的版本、连接后的上下行速度、会话传输量与已加载种子数。
- 查看当前服务的种子列表，并按名称、InfoHash、标签或保存路径检索。
- 查看种子的大小、进度、状态、实时速度、累计上下传、分享率、保存路径和添加时间。
- 批量或单个开始、暂停、删除种子；删除时可选择同时删除本地数据。
- 按需刷新，或为当前服务启用自动刷新。

该能力补足下载任务发送后的可见性和基础控制。MVP 不替代 Transmission Web UI，但模块边界须允许后续逐步迁入 TransGUI 的种子详情和高级管理能力，而不重写列表与基础操作。

## 范围与非目标

| 范围     | MVP 包含                                                    | MVP 不包含                                              |
| -------- | ----------------------------------------------------------- | ------------------------------------------------------- |
| 服务     | 从下载器设置列表进入单个已配置服务；Transmission 为验收实现 | 新增服务配置格式、服务端账号管理、服务端偏好设置        |
| 种子列表 | 当前服务的列表、关键字段排序与文本检索                      | 文件列表、Peer 列表、Tracker 编辑、队列优先级和移动目录 |
| 操作     | 开始、暂停、删除、可选删除数据                              | 强制校验、重新公告、限速、改名、标签编辑                |
| 刷新     | 手动刷新，间隔自动刷新，连续三次失败后暂停单服务刷新        | 后台常驻轮询、推送/WebSocket 更新、跨设备通知           |

后续下载器可沿用现有下载器工厂逐步接入；本期不以其他类型的兼容性作为发布门槛。非目标表示本期不交付，不表示模块不预留其数据与操作边界。

## 用户流程

1. 用户在“下载器设置”新增或编辑一个 Transmission 服务，地址可填写服务根地址或 RPC 地址。
2. 在该服务所在行点击“管理下载服务”入口，模块以该行的下载器 ID 打开。
3. 模块即时读取该 ID 对应的现有下载器配置；若配置已被删除、类型不受支持或连接失败，显示可恢复错误状态并提供返回设置的入口。
4. 用户在服务概览中查看版本、瞬时上下行、会话上下传和种子数量，并加载该服务的种子列表。
5. 用户在列表中检索、排序或多选种子，然后执行开始、暂停或删除。删除弹窗明确要求选择是否删除服务端本地数据。
6. 操作完成后仅刷新当前服务。自动刷新连续三次失败时停止当前服务的刷新，用户可在模块内手动恢复。

## 交互与信息架构

模块路由为 `/download-service/:downloaderId`，不出现在主导航。入口位于“下载器设置”列表每行的操作列，紧邻编辑、连接状态等既有操作。MVP 仅为 `type === "Transmission"` 且已启用的行展示可用入口；未启用服务需先在设置中启用，其他类型展示“暂不支持管理”的禁用操作提示。路由仍须独立校验配置，不能只依赖入口按钮的禁用状态。

模块页面在 MVP 由三个区域组成，未来种子详情区从当前选中的种子打开；详情内的“概览/文件/Tracker/Peer”视图各自按需加载，不要求 MVP 交付空白标签页：

```text
下载服务管理 / {下载器名称}
├── 服务概览：连接状态、版本、上传/下载速度、会话传输量、种子数
├── 操作栏：开始、暂停、删除、刷新、自动刷新、列配置、搜索
├── 种子表：名称/标签 | 大小 | 进度 | 状态 | 速度 | 累计量 | 分享率 | 路径 | 时间 | 操作
└── 后续扩展：所选种子的按需详情区（MVP 不渲染）
```

配置编辑始终留在“下载器设置”，管理模块不提供地址、用户名、密码、超时或启用状态编辑。实现参考 TransGUI 的核心交互原则：列表是主操作面，状态与错误在列表中可见，删除数据必须显式确认，刷新失败不能无限重试。参考项目本地路径为 `/Users/zhangqh/develop/project/transgui`；需要补充列表交互、下载服务协议规范、Transmission 管理、字段定义或后续详情能力的实现细节时，统一从该项目查阅，不为这些内容进行网络检索，但不作为当前项目的运行时依赖。TransGUI 的文件、Peer、Tracker 和带宽控制面板不纳入本期。

## 模块架构

### 职责与依赖方向

```text
下载器设置列表 -> /download-service/:downloaderId
                          |
          DownloadServiceManager (UI / 页面状态)
                          |
          download-service 用例 (查询 / 命令 / 能力校验)
                  /                  \
       配置读取端口               下载器管理端口
             |                         |
   现有下载器配置存储        现有下载器工厂 -> Transmission 适配器
                                             |
                                       Tauri HTTP -> RPC
```

| 层                                       | 负责                                                         | 不负责                          |
| ---------------------------------------- | ------------------------------------------------------------ | ------------------------------- |
| 设置列表与路由                           | 展示入口、传入下载器 ID、返回设置页                          | 维护管理页面状态或复制连接配置  |
| 管理模块 UI                              | 服务概览、列表、选择、详情容器、确认弹窗、可丢弃的页面状态   | 拼装 RPC 或保存服务凭据         |
| `src/application/download-service/` 用例 | 按 ID 读取配置、验证启用及能力、查询编排、批量命令与错误归一 | Vue 组件、Transmission 字段解析 |
| `src/packages/downloader/` 适配器        | RPC、协议版本差异、原始数据映射为管理契约                    | 路由、持久化、UI 通知           |
| 现有消息/平台适配                        | 将用例接到 `sendMessage` 与 Tauri HTTP，沿用现有实例缓存     | 引入第二个下载器配置源          |

建议以 `src/entries/options/views/DownloadServiceManager/` 放置路由页面、列表与视图状态，以 `src/application/download-service/` 放置可脱离 Vue 测试的用例及契约，继续在 `src/packages/downloader/entity/Transmission.ts` 内实现 Transmission 协议。MVP 可仅建立实际用到的文件，详情、文件、Tracker 等目录随着能力落地再添加；不要为了架构预设空实现或重命名所有旧代码。依赖保持 UI -> 用例 -> 端口 <- 适配器，下载器 package 不导入 options、消息总线或 Tauri API；这与现有桌面端架构优化设计一致。

### 配置与实例生命周期

`IDownloaderMetadata` 是唯一的服务配置来源；路由只持有 `downloaderId`，任何查询或命令都由用例按 ID 重新读取当前配置，再交给下载器工厂解析。UI 不发送地址、密码或完整配置作为命令参数。设置列表只负责导航，不持有管理状态。现有 `getDownloaderInstance()` 按关键连接字段变化重建实例，可复用该机制，但须避免新旧模块各维护一套连接缓存；配置删除、禁用、改类型后不得继续使用旧实例。

配置不存在或已禁用时停止请求并返回设置页引导；类型暂不支持时给出明确提示。切换路由中的服务 ID、离开页面或配置改变时，终止当前轮询、清空选中项，并隔离旧请求结果，避免不同服务的种子和操作状态串到一起。凭据继续走现有配置读取与网络边界；独立模块不额外保存或展示密码，也不把凭据附在路由、日志或错误文案中。后续凭据存储升级应由配置层统一完成，不在管理模块再做一次迁移。

### 管理能力契约

基础列表沿用 `CTorrent`、`TorrentClientStatus` 和现有下载器工厂，但它们主要服务于推送与概览，不能把未来的文件/Peer/Tracker 数据塞进 `CTorrent.raw` 供页面消费。用例向页面暴露精简且可序列化的服务概览、种子摘要以及 `TorrentRef = { downloaderId, torrentId }`；种子 ID 以当前服务为命名空间，InfoHash 仅用于展示与检索。所有速度统一为字节/秒、体积为字节、时间为 Unix 秒；后续 DTO 演进保持现有字段兼容，新增详情 DTO 独立定义。

目标用例契约如下，仅为设计接口，不表示当前代码已实现：

```typescript
getOverview(downloaderId): Promise<ServiceOverview>
listTorrents(downloaderId): Promise<TorrentSummary[]>
startTorrents(downloaderId, torrentIds): Promise<BulkResult>
stopTorrents(downloaderId, torrentIds): Promise<BulkResult>
removeTorrents(downloaderId, torrentIds, { deleteData: boolean }): Promise<BulkResult>
```

`ServiceOverview` 含连接/版本/速度/种子数及其更新时间；`TorrentSummary` 是列表所需字段，不含原始 RPC 响应；`BulkResult` 逐种子给出结果。概览和列表为独立查询，Transmission 概览可利用 `session-stats` 的 `torrentCount`，无需为了数量再次拉取全量种子。用例可先适配现有 `ProtocolMap` 的版本、状态、列表与单种子操作消息；新增批量契约时使用类型化输入/输出，不向 UI 暴露 `request(method, args)` 之类任意 RPC 入口。写命令必须验证配置、输入 ID 和服务端结果，批量操作返回每项成功/失败及可显示原因；若适配器支持一次 RPC 处理多个 ID，应在适配层合并请求，而不是页面无上限并发逐个提交。对非幂等删除禁止自动重试。

扩展能力采用按客户端声明的能力集合，例如 `torrent.files.read`、`torrent.files.write`、`torrent.trackers.write`、`torrent.verify`、`torrent.queue.write`、`session.settings.write`。能力不仅取决于类型，还可取决于服务端 RPC 版本；未支持时不展示或禁用对应操作，并给出原因。新增能力时为该领域新增类型化查询/命令和 DTO，由客户端适配器实现；不要求所有现有 `AbstractBittorrentClient` 子类同时实现大量新抽象方法。可以由独立的管理适配接口包装现有下载器实例，逐步扩展特定客户端能力；推送种子的 `addTorrent()` 接口保持不变。服务端能力判断必须在用例侧执行，不能只靠前端隐藏按钮。

### 页面状态与请求一致性

管理模块以当前 `downloaderId` 为状态作用域，维护 `loading`、`data`、`lastUpdatedAt`、`error`、`selectedTorrentIds`、`pendingOperations`。列表摘要按需或定时刷新；未来详情区采用所选种子的独立按需查询，不把文件和 Peer 全量放进列表轮询。轮询仅在页面可见且模块挂载时运行，刷新不重叠；切换服务/选择或卸载时释放定时器并忽略过期响应。连续三次失败停止自动刷新，保留并标记上次成功数据为过期；连接异常时禁用写操作，避免用户在陈旧数据上误删。

写操作进行中锁定相关种子与轮询结果的应用顺序，成功后重新查询受影响的列表/详情；失败展示具体失败项，不用“HTTP 成功”代替 RPC 成功。删除成功后清除对应选择与详情；未删除的失败项仍可定位。随着种子数量增长，列表与详情应分离请求，并根据实际性能决定增量刷新或虚拟滚动，而非首版引入复杂缓存框架。

### 与现有“我的下载器”关系

现有 `/my-client` 是跨服务聚合页面，其表格、批量操作和模块级共享定时器不能直接作为新模块的内部状态。MVP 保留旧路由和用户既有工作流，复用现有下载器适配器及传输路径；新模块单服务管理，通过独立用例和页面状态运行。后续若统一入口，由两种页面共同调用同一组管理用例，再按功能覆盖度决定废弃、跳转或保留聚合页；不得复制两套 Transmission RPC 实现。不能把“未来会迁移”当作本期移除旧页面的依据。

## 分阶段扩展路径

| 阶段         | 交付能力                                             | 保持稳定的边界                                             |
| ------------ | ---------------------------------------------------- | ---------------------------------------------------------- |
| MVP          | 单服务状态、种子列表与检索、开始/暂停/删除、刷新     | 路由只传 ID；配置单一来源；页面经类型化用例操作            |
| 种子详情     | 概览、文件及优先级、Tracker、Peer、活动信息          | 详情按种子 ID 懒加载；独立 DTO，不扩大列表响应             |
| 高级种子管理 | 校验、重新公告、队列、限速、标签、移动数据、批量操作 | 每种操作有明确参数、能力与确认规则；协议适配内处理版本差异 |
| 服务管理     | 会话设置、全局限速、磁盘与连接诊断                   | 服务级能力单独建模；配置仍由下载器设置统一管理             |
| 多客户端     | 按能力逐个接入其他下载器                             | 通用 UI 不依赖 Transmission 原始字段；未支持操作有明确降级 |

上表是架构预留和迁移顺序，不是 MVP 的交付承诺。每阶段先验证 TransGUI 对应工作流，再增加协议 DTO、用例和视图，最后评估与旧 `/my-client` 的功能重复。

## Transmission 映射

| Transmission RPC | MVP 用途       | 标准结果              |
| ---------------- | -------------- | --------------------- |
| `session-get`    | 连接检查、版本 | `ping()`、版本字符串  |
| `session-stats`  | 服务状态摘要   | `TorrentClientStatus` |
| `torrent-get`    | 种子列表       | `CTorrent[]`          |
| `torrent-start`  | 开始种子       | `boolean`             |
| `torrent-stop`   | 暂停种子       | `boolean`             |
| `torrent-remove` | 删除种子/数据  | `boolean`             |

状态映射：RPC 全局错误（`error > 0` 或 `errorString` 非空）优先显示为“错误”；其他状态为 `6 -> 做种`、`4 -> 下载`、`0 -> 暂停`、`2 -> 检查中`、`3/5 -> 排队中`，未识别值显示“未知”。

## 异常与安全

- 当前服务获取失败时保留上一次成功数据，并显示本次请求错误；不会向其他下载器发起请求。
- 自动刷新仅绑定当前服务实例；连续三次失败后停止该服务定时器，避免无效请求和错误提示泛滥。
- 删除只在用户确认后发起，并默认保留服务端数据。
- 下载器地址、用户名和密码继续由现有下载器配置流程管理；本 MVP 不新增日志记录，也不得在 UI 或日志输出密码。
- 下载服务本身可能位于局域网，真实环境验收需要用户提供可测试的 Transmission 实例；自动化只模拟 RPC 响应。

## 验收与测试

自动化覆盖：

- Transmission 的 409 会话协商与带会话 ID 的重试。
- `torrent-get` 请求包含错误字段，错误种子映射为 `CTorrentState.error`。
- 暂停、开始、删除只有 RPC 返回 `success` 时才返回成功。
- 用例在服务配置被删、禁用或类型变化后拒绝请求；切换下载器时旧响应不覆盖新页面。
- 批量命令区分全部成功、部分成功、全部失败，删除默认不删除数据且失败项不丢失。
- 轮询不重叠，切换路由和卸载后无定时器残留；详情请求未来可独立测试而不影响列表契约。

人工冒烟使用一个已启用的 Transmission：

1. 在“下载器设置”的 Transmission 行点击“管理下载服务”，确认进入的模块标题与配置名称一致。
2. 修改同一下载器的地址或认证信息后重新进入模块，确认请求使用更新后的配置，且没有第二份服务配置可编辑或保存。
3. 手动刷新，确认服务状态、版本与种子数可见。
4. 确认下载、做种、暂停和错误种子（若有）状态正确显示。
5. 对一个可恢复测试种子依次暂停、开始，确认 Transmission 端状态同步。
6. 对测试种子执行删除，分别验证保留数据和删除数据两种确认选项。
7. 将刷新间隔设为短值并断开服务，确认三次失败后服务被暂停且可恢复。
8. 在刷新请求尚未返回时离开模块或切换服务，确认旧响应不出现在新服务页面；返回后数据重新按当前配置加载。

通过条件：`pnpm check`、Transmission 单测和前端构建通过；上述人工冒烟在真实服务上完成后，才可声明该集成已完成真实环境验收。
